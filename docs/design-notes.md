# 風控持倉模型：設計筆記

扁平持倉原型（`src/flat/`）背後的分析與結論。原型本身的規則與用法見 `src/flat/README.md`。

## 背景：現行系統

- **計算鏈**：工作線程定時取行情與持倉快照，依序算
  `持倉明細 → 持倉合計（由明細衍生）→ 帳戶保證金合計（需委託、明細、合計都算完）`。
  過程中讀取匯率、保證金模板、品牌模板、產品配置。
- **持倉明細有多個寫入者**：
  - 消費線程依交易異動減倉、刪除持倉
  - 工作線程寫入最新價相關欄位
  - 強平時直接在明細上加「待平手數」物件

  目前用「記錄每個欄位由哪條線程異動」來管理。
- **barrier**：工作線程每輪一起計算；每輪開算前也藉此確認配置有沒有變更。
- **資料模型**：用戶主體下有持倉、帳戶、委託模型。持倉模型（鍵為主帳戶 + 產品）包含明細與合計，
  同時被用戶維度 map 與產品維度 map 持有。委託模型是同樣的結構。
- **邊界條件**：
  - 不存在跨帳戶計算
  - 下單前風控檢查由交易服務負責，不在風控服務內

## 1. 欄位級所有權擋不住的三個情境

每個欄位只有一個寫入者，**不能保證跨欄位的一致性**，而風控最嚴重的 bug 都出在跨欄位上。

| 情境 | 過程 | 後果 |
|---|---|---|
| 浮盈新舊混搭 | 消費線程平倉時先改數量、後改均價；工作線程在兩者之間讀取 | 用新數量配舊均價算浮盈 |
| 強平超量 | 工作線程依快照寫入「待平 10 手」，同時用戶自己平掉 6 手，持倉剩 4 | 強平單一送出就反手開倉 |
| 孤兒寫入 | 消費線程刪除持倉，工作線程仍握著指標 | raw pointer 會 use-after-free；shared_ptr 則是寫進已脫離容器的物件 |

另外，**單一寫入者不等於可見性**。欄位如果是普通的 `double`，跨線程讀寫仍然是 data race。
而且所有權規則只存在文件裡，編譯器不會幫你檢查。

### 修正原則：所有權按「不變量群組」劃分

**參與同一個不變量的欄位，必須屬於同一個擁有者。**（對應 DDD 的 aggregate / consistency boundary）

| 群組 | 欄位 | 唯一擁有者 |
|---|---|---|
| 持倉核心 | 數量、均價、**待平手數**、狀態 | 消費線程（交易事件） |
| 估值 | 最新價、浮盈、保證金占用 | 工作線程，從不可變的核心快照與行情快照計算 |
| 強平 | 不是欄位，是**命令** | 工作線程發出，消費線程依當下真實持倉檢查後執行 |

強平改成「發命令、由擁有者執行」之後，檢查和扣減發生在同一條線程、同一個時間點，超量在結構上就不可能發生。

## 2. barrier 拆成三個職責

barrier 現在同時在做三件不同的事。用一個同步原語扛三件事，代價是所有線程互相等待，最慢的那一條決定整體節奏。

| 職責 | 替代方案 |
|---|---|
| 一輪內的配置一致性（算到一半配置不能換） | **組合配置快照**：把所有配置組成一個不可變的 `shared_ptr<const ConfigSnapshot>`，每輪開始只取一次指標，整輪都用它 |
| 輪與輪之間的變更偵測 | 快照帶版本號，比對一個整數即可 |
| 跨線程的階段順序（明細 → 合計 → 保證金） | **按主帳戶分片**，同一帳戶的整條計算鏈在同一條線程內依序執行 |

組合快照的額外好處：

- **相關的配置可以一起發布**，例如匯率和保證金模板同一次調整。barrier 擋不住「新匯率配舊模板」的情況。
- **發布前先 validate**，不通過就保留舊版並告警。對風控來說，配置更新失敗時繼續用舊的算，遠比用一份壞掉的配置算安全。
- **複製成本只有幾個指標**，沒變動的配置是共享的。

進一步可以做**配置編譯**：在發布時，把「帳戶 → 品牌模板 → 保證金模板 → 產品配置 → 匯率」的逐層解析，
預先展開成 `(帳戶群組, 產品) → 參數` 的查表。熱路徑每筆只需 O(1) 查一次，展開後的表也能直接 dump 給 QA 核對。

## 3. 物件圖 → 扁平表

現行模型彆扭的根源是**同一個持倉物件有兩個擁有者**（用戶維度 map 和產品維度 map）：

- 新增和刪除要同步兩邊，漏一邊就產生孤兒或殘留
- 生命週期由 shared_ptr 決定，物件什麼時候真正消失、在哪條線程上被釋放，都不明確
- 事實（明細）和衍生（合計）綁在同一個物件裡，修改點散落各處

扁平化的三條規則（原型已實作）：

1. 每種實體一張主表，主表是唯一擁有者，以穩定 ID 為鍵
2. 衍生資料獨立成表，只能由重算產生，整列覆蓋，從不局部修改
3. 索引只存 key，由 Boost.MultiIndex 在 insert / modify / erase 時自動同步

原本的「持倉模型」不再是一個物件，而是一個**查詢**。

## 4. 風控適不適合事件機制

**適合的部分**：

- 風控的輸入（成交回報、行情、配置變更、出入金）本來就是事件
- 把「修改持倉」收斂成「處理事件」，只是把現狀整理清楚

原型採混合式：**修改走事件，計算維持批次**。事件只標記 dirty，重算按節奏批次執行。

**不適合直接照搬的部分**：

1. **行情不能逐筆觸發完整計算**。行情只標 dirty、批次重估，否則會被行情淹沒。
2. **恢復機制是最大成本**。完整的事件溯源需要可靠的事件 log（或快照加之後的事件）。
   如果權威狀態是資料庫裡的持倉，「可重放」在生產環境就不是免費的。
3. **上游的序號與重送語意**。成交回報若可能重複或亂序，就需要冪等與去重。

**結論**：修改收斂成事件、計算維持批次，適合。完整的事件溯源要先回答第 2、3 點。
可以先只在測試環境錄事件、做重放比對，拿到可測試性的好處，不必改變生產環境的持久化方式。

## 5. DB 同步緩衝區的五項檢查

「業務線程寫 buffer、同步線程定時取出寫 DB」這個模式，先取到區域變數是對的：
它把持鎖時間從「DB I/O 的時間」縮短成「交換一次指標的時間」。要檢查的是：

1. **鎖內是 `swap` 還是逐筆 copy**：要用 `local.swap(buffer_)`，O(1)；`local` 設成成員變數，`clear()` 後保留 capacity 輪流使用。
2. **buffer 裡放的是值，還是指向活物件的指標**：放指標的話，鎖外讀取時物件可能正在被改。
3. **狀態型和事件型有沒有分開**：
   - 狀態型（持倉、餘額）可以合併，只保留最後一次
   - 事件型（成交、流水）每筆都要落地，不能合併
4. **是否逐筆 commit**：改成一批一個 transaction，並使用 bulk upsert。
5. **寫失敗時資料去哪了**：
   - 直接 `clear()` 會默默遺失資料
   - 塞回 buffer 可能蓋掉更新的值，要用「key 不存在才放回」，或帶版本號的冪等 upsert
   - 成交這類事件不能遺失，要同步寫入、先寫 WAL，或確保上游能重送

第 5 點答不出來的話，優先順序高於效能。

## 6. 落地順序

依風險排列，每一步都可以獨立上線：

1. **待平手數歸到消費線程，強平改發命令**。後果是錯誤開倉，風險最高，改動範圍卻最小。
2. **組合配置快照加版本號**。移除 barrier 的前兩個職責，改動集中在配置服務與工作線程取配置的地方。
3. **估值從持倉物件拆出來，核心改發不可變快照**。解決浮盈錯算和孤兒寫入。
4. **配置編譯成查表**。純效能改善，可以和舊算法逐筆比對結果來驗證。
5. **扁平模型 + 按主帳戶分片 + 增量重算**。動到計算主架構，等前面穩定、量過確定瓶頸在這裡再做。

改之前，先畫出現在每條線程在 barrier 上等的是誰，再決定要做到哪一步。
